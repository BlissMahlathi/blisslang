# BlissLang

A section-driven web development language with a pure-Rust compiler. Zero npm. Zero axum. Zero tokio. Zero external HTTP dependencies of any kind.

**Author:** Bliss Mahlathi — PulseBit, Nkowankowa, Limpopo, South Africa

> Build websites section by section. Build enterprise systems without fear.

---

## Why BlissLang exists

Modern web development pulls in hundreds of transitive npm dependencies for a single project — any one of which can be compromised in a supply-chain attack. BlissLang takes the opposite approach: the entire toolchain, from lexer to dev server, is a single Rust binary built on the standard library. `cargo build`, copy the binary, done. No `node_modules`. No `package-lock.json`. No surface area for someone else's malicious package to reach your production server.

## How it all fits together

```
.section / .page / .div file (BlissLang source)
        │
        ▼
  ┌──────────┐
  │  Lexer   │  src/compiler/lexer.rs
  └────┬─────┘  Indentation-sensitive tokenizer
       │
       ▼
  ┌──────────┐
  │  Parser  │  src/compiler/parser.rs
  └────┬─────┘  Recursive descent → typed AST
       │
       ▼
  ┌──────────┐
  │   AST    │  src/compiler/ast.rs
  └────┬─────┘  Node definitions for every BlissLang construct
       │
       ├──────────────┬──────────────┐
       ▼               ▼              ▼
  ┌─────────┐    ┌───────────┐  ┌──────────────┐
  │TypeCheck│    │  Renderer │  │  GeoPlotter  │
  └─────────┘    └─────┬─────┘  └──────┬───────┘
  compiler/      compiler/        geo/math.rs
  typechecker.rs renderer.rs      geo/plotter.rs
                       │
                       ▼
                  HTML + purged CSS
                  (compiler/style.rs)
                       │
                       ▼
              ┌─────────────────┐
              │   Dev Server    │  runtime/server.rs
              └────────┬────────┘  std::net + thread pool
                       │
                       ▼
              Browser ← hot reload (SSE) + signals (runtime/signals.rs)
```

Every box above is a real file in `src/`. Nothing is generated by a third-party crate — the lexer, parser, renderer, math engine, CSS compiler, and HTTP server are all hand-written.

## Module-by-module walkthrough

### 1. The Lexer — `src/compiler/lexer.rs`

Converts raw BlissLang source text into a stream of tokens. BlissLang is indentation-sensitive, like Python — the lexer tracks an indent stack and emits synthetic `Indent`/`Dedent` tokens so the parser never has to count spaces itself.

```bliss
BuildSection[name: "Hero"]:
    h1[text: "Hello"]
```

becomes the token stream:

```
BuildSection  [  name  :  "Hero"  ]  :  NEWLINE
INDENT
h1  [  text  :  "Hello"  ]  NEWLINE
DEDENT
EOF
```

A tricky bug we hit early: multi-line attribute lists like

```bliss
BuildSection[
    name: "Hero",
    style.tailwind: "bg-slate-900"
]:
```

were emitting spurious `Indent`/`Dedent` tokens *inside* the brackets, because the lexer doesn't know it's inside `[...]` when it sees a newline. The fix lives in the parser's `parse_attr_list()` — it explicitly skips `Newline`/`Indent`/`Dedent` tokens while scanning attribute key-value pairs, since whitespace inside brackets is never semantically meaningful.

### 2. The AST — `src/compiler/ast.rs`

Defines every node type BlissLang can produce: `PageNode`, `SectionNode`, `DivNode`, `ElementNode`, `StateNode`, `AnimationNode`, and so on. This is the contract between the parser (which builds these) and the renderer/typechecker (which consume them). Attribute values are typed as `AttrValue::Str | Number | Bool | Null | Array | Expr | Interpolated` so downstream code never has to guess what kind of value an attribute holds.

### 3. The Parser — `src/compiler/parser.rs`

A hand-written recursive descent parser — one function per grammar rule. `parse_section()` calls `parse_attr_list()` calls `parse_attr_value()`, and so on. No parser generator, no external crate.

One subtlety: keywords like `from`, `to`, `as`, and `var` are reserved for constructs like `ForEach...as item track "id"` and `repeat[i from 0 to 10]` — but they're also completely valid attribute keys, as in `line[from: "0 0", to: "100 100"]`. The `expect_ident()` function explicitly maps these keyword tokens back to their lowercase source text when they appear in identifier position, so `from:` in a `line[]` shape parses as the string `"from"`, not as the keyword.

### 4. The Renderer — `src/compiler/renderer.rs`

Walks the AST and produces the final HTML string. This is where most of BlissLang's "magic" attributes get translated into real HTML:

```bliss
h1[
    text: "Welcome",
    style.tailwind: "text-6xl font-bold text-white",
    animate: "fadeInUp",
    animate.trigger: "scroll"
]
```

becomes:

```html
<h1 class="text-6xl font-bold text-white" data-animate="fadeInUp" data-animate-trigger="scroll">
  Welcome
</h1>
```

The `data-animate-*` attributes are read by the JS runtime (see §7) which wires up an `IntersectionObserver` to fire the CSS keyframe animation when the element scrolls into view.

**Props interpolation.** Inside a `BuildDiv`, you can reference props with `{props.name}`:

```bliss
BuildDiv[name: "Card"]:
    Props:
        title: String, required

    h3[text: "{props.title}"]
```

`interpolate_string()` in the renderer walks the string character by character, finds `{props.title}`, and substitutes the actual value passed by the caller. If the expression can't be resolved at compile time (e.g. it references a runtime signal), it's left as `{{expr}}` for the JS signal system to fill in at runtime instead.

### 4.5. Shared layouts — `layout:` and `Slot["content"]`

You do **not** have to repeat `IncludeSection["NavBar"]` and `IncludeSection["Footer"]` on every page. Create one layout page marked `is_layout: true`, with a `Slot["content"]` marking where each page's unique body goes:

```bliss
# Pages/LandingPage/MainLayout.page
BuildPage[name: "MainLayout", is_layout: true]:
    IncludeSection["NavBar"]

    Slot[name: "content"]

    IncludeSection["Footer"]
```

Every real page then just says which layout to use and includes only its own unique content:

```bliss
# Pages/LandingPage/Home.page
BuildPage[name: "Home", route: "/", title: "Home", layout: "MainLayout"]:
    IncludeSection["HomeBody"]
```

```bliss
# Pages/LandingPage/About.page
BuildPage[name: "About", route: "/about", title: "About", layout: "MainLayout"]:
    IncludeSection["AboutBody"]
```

The renderer's `resolve_layout_chain()` walks `layout:` references (supporting nested layouts, e.g. a `DashboardLayout` inside a `MainLayout`), composing each page's rendered body into the parent layout's `Slot["content"]`. A page with `is_layout: true` is registered for lookup but never gets its own route — it only exists to be reused, so `bliss build` will not emit a standalone HTML file for it.

This is the answer to "do I have to include NavBar/Footer on every page": no — use `layout:`. `UseDiv` is for *reusable components inside a section's body* (cards, stat widgets); `layout:` is for *the page shell itself*. Don't reach for a Div to wrap an entire page — that's what layouts are for.



A from-scratch recursive descent expression evaluator — no `evalexpr` crate, no `meval`. Supports the full set of functions BlissGeo needs: `sin`, `cos`, `tan`, `sqrt`, `pow`, `log`, `lerp`, `clamp`, `atan2`, and more, plus the constants `PI`, `E`, `TAU`.

```rust
eval("sin(x) * 100", &[("x", 1.5708)])  // → ~100.0
```

This same evaluator is what powers `plot[]`, `parametric[]`, `polar[]`, and `spiral[]` in BlissGeo — every coordinate on those curves is computed by walking this tokenizer → parser → evaluator pipeline once per sample point.

### 6. The Geo Plotter — `src/geo/plotter.rs`

Converts BlissGeo declarations into real SVG path data, using the math engine for every point:

```bliss
DrawCanvas[width: 400, height: 200]:
    plot[
        fn:      "sin(x)",
        x.range: "0 to 6.283",
        y.scale: 80,
        origin:  "0 100",
        color:   "#E94560"
    ]
```

`render_plot()` samples the function across the range (default 200 steps), evaluates `sin(x)` at each step via `geo::math::eval`, and stitches the points into an SVG `<path d="M x0 y0 L x1 y1 L x2 y2 ...">`. The same pattern powers `parametric[]` (two functions, one for x and one for y, both driven by a shared `t`), `spiral[]` (archimedean/logarithmic/fermat formulas), and `regularPolygon[]` (vertex angles computed directly, no sampling needed).

### 7. The Signal System — `src/runtime/signals.rs`

This file generates the JavaScript reactivity engine that gets embedded into every page's runtime bundle. It's vanilla JS — no React, no Vue, no framework — built around `signal()`, `derived()`, and `effect()`:

```javascript
var count = bliss.signal(0);
bliss.effect(function() {
    document.title = 'Count: ' + count.get();
});
count.set(5); // title updates automatically
```

`signal()` tracks subscribers; when an `effect()` reads a signal via `.get()`, it automatically subscribes itself, so dependency tracking is implicit — you never have to declare a dependency array like you would in React's `useEffect`.

On the Rust side, `render_state_init()` in `renderer.rs` reads a `CreateState[]` block from the AST and emits the matching JS:

```bliss
CreateState[name: "App"]:
    cart: Signal[type: List, default: []]
    cartCount: Derived[from: "cart", compute: "cart.get().length"]
```

becomes a `<script>` block in the page:

```javascript
window.__bliss.state.App = {
  cart: window.__bliss.signal([]),
  cartCount: window.__bliss.derived(function() {
    var s = window.__bliss.state.App;
    return cart.get().length;
  })
};
```

### 8. The ForEach Runtime Loop

`ForEach["State.App.items"] as item:` doesn't render items at compile time — it can't, since the data is only known at runtime. Instead, the renderer emits a container and a hidden `<template>`:

```html
<div data-foreach="State.App.items" data-binding="item">
  <template data-foreach-item>
    <p>{{name}}</p>
  </template>
</div>
```

The signal system's `bindDOM()` (in `signals.rs`) watches the `items` signal; whenever it changes, it clones the template once per array item, replaces `{{field}}` placeholders with the item's actual values, and appends the clones to the container.

### 9. The Style Compiler — `src/compiler/style.rs`

This is what eliminated the `cdn.tailwindcss.com` dependency. Instead of shipping a multi-megabyte JIT compiler to the browser, BlissLang does the work at build time on the Rust side:

1. `extract_classes()` scans every rendered HTML page for `class="..."` values
2. Each class is looked up in a built-in registry of ~200 common Tailwind utilities (`lookup()`)
3. `generate_css()` writes out only the CSS rules actually used, including responsive prefixes (`md:`, `lg:`) and pseudo-states (`hover:`, `focus:`)

The result is a tiny, self-contained `<style>` block with zero network requests and zero unused CSS.

### 10. The Type Checker — `src/compiler/typechecker.rs`

Runs after parsing, before rendering. Catches mistakes a runtime error never would:

- Unknown HTML tags (`<diiv>` instead of `<div>`)
- Invalid `animate.trigger` values (only `scroll | load | hover | click` are valid)
- Tailwind class typos, with suggestions (`bg-bloo-500` → did you mean a real color?)
- Missing required attributes on BlissGeo shapes (`circle` needs `center` and `radius`)
- `javascript:` URIs in `href` (blocked outright — a basic XSS guard)
- References to sections/divs that don't exist in the project

```
$ bliss check Sections/Hero.section
  ✓ 170 tokens
  ✓ Parsed as Section
  ✓ No syntax or type errors
All checks passed.
```

### 11. The Config Parser — `src/compiler/config.rs`

Parses `bliss.config`, a hand-written TOML-like format (no `toml` crate dependency). Drives every compiler decision: output mode (`static | runtime | hybrid`), security level, dev server port, i18n locales, and package pins.

```toml
project:    "MyApp"
output:     "static"
security:   "strict"
i18n:
    default: "en"
    locales: ["en", "zu"]
```

`validate()` catches dangerous configurations before they ship — `security: "open"` triggers a critical warning, and any package pinned with a version range (`^3.0.0` instead of an exact `3.0.0`) is flagged, since BlissLang's security model requires exact, hash-verified dependency pins.

### 12. The Dev Server — `src/runtime/server.rs`

Pure `std::net::TcpListener` — no axum, no tokio, no hyper. A hand-built thread pool dispatches each incoming connection to a worker thread. Hot reload works via Server-Sent Events: the `notify` crate (a well-audited file watcher, used by `cargo` itself) watches the project directory, and when a `.section`/`.page`/`.div` file changes, the server rebuilds the affected pages and pushes a `reload` event down the open SSE connection at `/_bliss/reload`. The browser's tiny JS client listens for that event and calls `window.location.reload()`.

### 13. The Release Pipeline — `src/main.rs` (`cmd_release`)

`bliss release` runs the full production pipeline in one command: load → type-check (fails the build on any error) → render → minify HTML/JS → write to `dist/`. It reports byte savings per page so you can see exactly what shipped.

```
$ bliss release MyApp
Type checking...
  ✓ All type checks passed

Building...
  ✓ dist/index.html (10031 → 9311 bytes, 8% smaller)
  ✓ dist/_bliss_runtime.js (23026 bytes)

Release ready. Deploy the dist/ folder.
```

### 14.5 PWA & Mobile — `src/compiler/pwa.rs`

Implements spec Part 19. When `bliss.config` has a `pwa:` block:

```toml
pwa:
    enabled: true
    name: "MyApp"
    theme_color: "#1A1A2E"
    icons:
        - src: "@Images/icon-192.png"
          sizes: "192x192"
          type: "image/png"
    offline_page: "/offline"
    cache_strategy: "network-first"   # or cache-first | stale-while-revalidate
    cache_pages: ["/", "/dashboard"]
    push_notifications: true
```

`bliss build` / `bliss release` will write three extra files alongside the HTML:

- `manifest.json` — built directly from the config, including the `icons` array (with `purpose: "maskable"` support).
- `sw.js` — a hand-written service worker whose fetch handler is generated per the configured `cache_strategy`, precaching `cache_pages` plus the `offline_page`, and (if `push_notifications: true`) wiring up `push` / `notificationclick` listeners.
- `_bliss_pwa.js` — the client runtime: registers `sw.js`, and exposes `window.PWA` with `pushSupported()`, `pushSubscribed()`, and `requestPushPermission()` (matching the `PWA.*` calls used in the spec's `OnMount`/`Async` examples), plus `canInstall()`/`promptInstall()` built on `beforeinstallprompt`.

The `icons:` field is a list of tables, which `compiler::config`'s generic key/value parser doesn't yet handle — so `pwa.rs` parses the `pwa:` block directly from the raw config text instead of going through `ConfigValue`. The type checker also enforces that any page marked `pwa.offline: true` has `output: "static"`, since the offline fallback has to render with no network access.

Responsive breakpoints (`OnMobile:` / `OnTablet:` / `OnDesktop:`, spec §19.4) were already implemented in the lexer/parser/renderer before this — `Child::Responsive` renders to a `bliss-mobile-only` / `bliss-tablet-only` / `bliss-desktop-only` class, hidden/shown by the base CSS per breakpoint.

### 15. Project Scaffolding — `src/runtime/scaffold.rs`

`bliss new MyApp` generates a complete working project — directory structure, a `bliss.config`, a `Landing.page` with `Hero`/`Features`/`Footer` sections, a reusable `Card` div, an `AppState` with example signals, locale files in English and isiZulu, and a `README.md`. Every generated file is verified to pass `bliss check` before being shipped as a template.

## CLI reference

```
bliss new <name> [--template landing|dashboard|minimal]
    Scaffold a new project.

bliss dev [project] [--port 8080] [--no-reload] [--threads 4]
    Start the dev server with hot reload.

bliss build [project] [--out dist]
    Build to static HTML/CSS/JS — no minification, no type-check gate.

bliss release [project] [--out dist]
    Production build: type-checks (fails on error), minifies, reports savings.

bliss check <file>
    Lex + parse + type-check a single file.

bliss tokens <file>
    Print the raw token stream (debug tool).

bliss ast <file>
    Print the full parsed AST (debug tool).

bliss info [project]
    List all pages, sections, divs, and states in a project.
```
